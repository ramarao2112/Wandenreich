# TC-002: OWNERSHIP-CHECK

## Overview
- **Rule ID:** `TC-002`
- **Rule Name:** `OWNERSHIP-CHECK`
- **Severity:** `Error`
- **Target:** Endpoint authorization policies

## Trigger
An endpoint declares an invalid, unsupported, or contradictory authorization policy per compiler specification §B4:
1. **Role-only policy (`role_only: NAME`):** RBAC is unsupported in TrustSpec v1.
2. **Wrong field equality in `authorize:`:** An equality predicate (`FIELD == current_user.id`) names an existing field that is not the declared resource ownership field (e.g. `id` instead of `owner_id`).
3. **Public owned creation (`POST /collection` with `auth: public`):** Creating an owned resource requires an authenticated caller identity to assign ownership.
4. **Public User endpoint or waiver:** The `User` resource is strictly self-only in v1 (`GET /users/{id}`); public access or ownership waivers are forbidden.
5. **Authorize on unowned resource:** An ordinary unowned resource has no ownership field to enforce.
6. **Contradictory declarations:** Declaring `auth: public` together with any `authorize:` predicate.
7. **Creation waiver / predicate:** An owned `POST` endpoint declaring an `authorize:` predicate. Creation automatically assigns the authenticated caller as owner; ownership waivers and predicates do not apply to creation. Supported waivers apply to list, read, update, and delete operations (`GET /collection`, `GET /collection/{id}`, `PUT /collection/{id}`, `PATCH /collection/{id}`, `DELETE /collection/{id}`).

## Rationale
Broken or unsupported authorization policies lead to broken object-level authorization (BOLA/IDOR) vulnerabilities, insecure defaults, or runtime authorization crashes. TrustSpec enforces coherent, verifiable ownership models consistent with specification §B4.

## Fix Options
- For **owned creation (`POST`)**:
  - Declare `auth: required` and omit `authorize:`. Creation automatically records the authenticated caller as the resource owner; `authorize:` predicates and waivers are forbidden on creation.
- For **owned existing item / list operations (`GET`, `PUT`, `PATCH`, `DELETE`)**:
  - Use default owner check by omitting `authorize:` on `auth: required` endpoints (filters lists to owner; checks owner on item routes).
  - Or declare explicit matching ownership equality for item operations: `authorize: <ownership_field> == current_user.id` (legal redundant declaration; forbidden on `POST`).
  - For deliberate ownership waivers: declare `authorize: public` on `auth: required` endpoints for list, read, update, or delete operations (waives ownership check while requiring caller login; supported per §B4).
- For **User endpoints**:
  - Ensure `auth: required` is declared without waivers. Access is strictly limited to the authenticated user themselves (`self-only`).
- For **unsupported roles (`role_only`)**:
  - On `POST`: Remove `role_only`; caller is assigned as owner upon creation under `auth: required`.
  - On `GET`, `PUT`, `PATCH`, `DELETE`: Remove `role_only` and use owner-based controls (`authorize: <ownership_field> == current_user.id`), omit `authorize:` for default owner checks, or use `auth: required` for login-only access.
